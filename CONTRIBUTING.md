# Внесення змін

## Початок задачі

Відкрийте репозиторій як робочий каталог. Прочитайте AGENTS.md, конституцію й відповідну специфікацію. Перевірте git status і створіть гілку для однієї змістовної задачі. Агент не пушить у main та не зливає PR без прямого погодження власника.

## Spec Kit

Установлення й сумісність: [docs/codex-speckit.md](docs/codex-speckit.md). Використовуємо specify-cli 1.3.2, codex skills, Python-скрипти, events=false. Кроки виконуються агентом, а не термінальними командами з такими самими назвами.

Для суттєвої зміни:

1. `$speckit-specify` — вимоги й сценарії, без передчасного вибору реалізації.
2. `$speckit-clarify` — за суттєвої неоднозначності; відомі рішення користувача не перепитувати.
3. `$speckit-plan` — рішення й обмеження конкретного репозиторію.
4. `$speckit-tasks` — конкретні кроки за сценаріями.
5. `$speckit-analyze` — узгодженість і покриття перед реалізацією.
6. `$speckit-implement` — виконання завдань і перевірка результатів.
7. `$speckit-converge` — пошук залишкових розривів; за потреби повторити implement/converge.

Конституцію оновлює `$speckit-constitution`, коли справді змінюються принципи. У поточній сесії без автоматичного виявлення skills агент читає встановлений SKILL.md й виконує його кроки явно, записуючи це обмеження. Не симулювати виклик команд, хуків чи незалежного агента.

Проста правка репліки, імені або джерела може послатися на чинну специфікацію й пояснити, чому новий пакет не потрібен. Для зміни правил, форматів, pipeline або розширення вимог спочатку оновлюємо відповідну специфікацію чи створюємо нову. PR потрібен в обох випадках.

## Pull request

Початковий стан — draft. Опис за шаблоном: проблема/мета, межі, джерела, специфікація, перевірки й відкриті питання. Фіксуйте фактичний результат команди та її межі: text CI не прослуховує звуку й не підтверджує міміку. Не змінюйте статус погоджених матеріалів лише тому, що validator пройшов.

Перевірки перед готовністю:

```text
python pipeline/validate.py
git diff --check
```

Додайте коротку реальну перевірку зміненого інструмента, якщо вона потрібна. Для великих ML/media запусків спочатку skill runtime-diagnostics. Моделі, медіа, environments, конфігурації авторизації та токени не включати до diff.

Коли пропозиція готова, можна перевести її в ready for review й попросити розгляд; це не згода на злиття. Власник явно погоджує актуальний склад змін. Нові змістовні коміти після цього повертають потребу перегляду. Невирішені блокувальні зауваження мають бути видимими. Без погодження не використовувати merge, auto-merge або прямий push у main.

Це процесна домовленість. Захист main чи обов'язкові GitHub approvals у налаштуваннях репозиторію в цій зміні не вмикаються; не стверджувати, що сервер технічно блокує порушення.

## Інші моделі

Для локального Copilot CLI використовуйте опціональний [copilot-delegation](.agents/skills/copilot-delegation/SKILL.md): агент може запропонувати реалізацію, дослідження або рев’ю, а запуск виконує за дорученням власника. Результат реалізації перевіряє основний агент; звіт виконавця не є незалежним рев’ю. Skill не змінює правил PR і погодження злиття.

На окреме доручення власника можна залучити незалежну модель до конкретного питання: джерел/літературного контексту, мовної природності або технічного рішення. Інструкції виконавцям не замінюють факти із джерел. Шаблон: [templates/model-review.md](templates/model-review.md).

Для кожного висновку вказати модель і доступну версію, переглянутий head SHA або точний контекст, предмет, докази та обмеження. Зауваження мають ID і рішення: accepted, rejected або deferred з причиною та блокувальністю. Відхилена думка не зникає з історії. Зміна head позначає стару рецензію як застарілу або вимагає явного повторного зіставлення.

Самоперевірка автора не є незалежним рецензуванням. Коли інша модель недоступна або не доручена, записати «не виконано»; не імітувати її відповіді й не вважати відсутність висновку згодою. Навіть одностайність моделей не підтверджує джерельний факт і не дає права злиття.
