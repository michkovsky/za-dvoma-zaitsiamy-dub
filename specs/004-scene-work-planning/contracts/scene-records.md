# Контракт текстових реєстрів сцен

Контракт реєстрів, реалізований у pipeline/scene_validation.py; фактичні перевірки — [quickstart.md](../quickstart.md). CSV UTF-8 зі штатним екрануванням; час HH:MM:SS.mmm, кінець виключний. Offset — десяткові секунди зі знаком. Семантика — [модель](../data-model.md).

| Файл | Заголовок |
| --- | --- |
| scenes/index.csv | id,title,start,end,status,source_id,lifecycle,revision,package |
| scenes/coverage.csv | id,source_id,start,end,kind,scene_id,status,note |
| source/timing.csv | source_id,duration,reference_source_id,offset,note |
| scenes/changes/index.csv | change_id,type,state,from_scene,from_revision,to_scene,to_revision,record |
| scenes/*/dialogue.uk.csv | id,start,end,speaker,text,status,note,source_id |

## Сумісність

- Нові колонки додаються справа; P001 не мігрується. Нові сценові рядки вимагають source_id часової шкали.
- Мовні dialogue.csv/performed.csv не змінюють значення source_id — це оригінальна репліка. Пошук глобальний, без припущення про каталог із префікса. Хор допускає кілька performed-рядків на один source_id, кожен із власним id.
- Change-index має складений ключ із моделі; інші id — унікальні в таблиці, репліки — глобально в усіх canonical dialogue.uk.csv, включно з пілотом.
- Scenes/index містить останню ревізію кожного ID. Попередні межі й ревізії беруться з change-record та Git; історичні кінці ребер не зобов'язані збігатися з поточною revision.

## Структура change-record

Паспорт; докази й причина; таблиці до/після; повний перелік матеріалів; таблиця old_ref,new_ref,decision,recheck; пакети-наступники й перерозподіл завдань; рішення щодо погоджень; відкриті питання; результат перевірки покриття й посилань. Ref — відносний шлях плюс сталий ID або заголовок; машинні абсолютні шляхи заборонені.

### Машинозчитувані блоки change-record

Для перевірки історичних версій, proposed-оголошень і резервування ID record містить рівно три обов'язкові розділи з точними заголовками `## Change metadata`, `## Before`, `## After`. Відразу після кожного заголовка, пропустивши лише порожні рядки, стоїть один fenced-блок із позначкою `csv`; відкривальна та закривальна огорожі — рівно три backtick без відступу. Поза цими розділами опис і редакторські таблиці довільні. Інші code-блоки не є структурними даними й не замінюють обов'язкові.

Усередині кожного блоку — стандартний CSV: фіксований порядок колонок, перший рядок — заголовок, без зайвих/відсутніх колонок, порожніх рядків і багаторядкових клітинок. Пробіли навколо CSV-значень не додаються; ID й enum чутливі до регістру. Екранування ком і лапок — стандартне CSV. Повтор зарезервованого заголовка розділу, відсутній блок, незакрита огорожа або некоректний CSV — помилка. Парсер читає лише явно огороджені блоки, не виводить поля з довільного тексту.

HTML-коментарі поза fenced code/CSV не створюють розділів і не рахуються дублями; їх пропускають без зміни номерів рядків. Усередині fenced CSV текст на кшталт `<!--literal-->` зберігається як значення клітинки й проходить звичайну перевірку семантики поля, а не видаляється як коментар.

| Розділ | Точний CSV-заголовок | Кількість рядків даних |
| --- | --- | --- |
| Change metadata | change_id,type,state,decision | рівно 1 |
| Before | scene_id,revision,source_id,start,end | ≥1, унікальні scene_id/revision |
| After | scene_id,revision,source_id,start,end | ≥1, унікальні scene_id/revision |

`change_id`, `type` і `state` точно збігаються з усіма рядками цієї зміни в changes/index.csv; record цього індексу вказує на поточний файл. Type — boundary/split/merge, state — proposed/applied. Для proposed decision — pending або rejected; для applied — accepted. Відхилений record залишається в індексі як proposed/rejected, зберігаючи резерв нових ID; до applied-графа він не входить і поточну карту не змінює.

Множина пар scene_id/revision у Before точно дорівнює множині from_scene/from_revision ребер зміни, а After — множині to_scene/to_revision. Один snapshot на пару незалежно від кількості ребер. Дублікати, зайві snapshots і відсутні кінці ребер відхиляються. Межі мають формат HH:MM:SS.mmm та задовольняють 0 ≤ start < end ≤ duration відповідного source_id. Revision — додатне ціле; source_id відомий, зі встановленою тривалістю. Усі snapshots однієї зміни використовують спільне джерело video; зміна джерела не є boundary/split/merge.

Before має описувати наявні версії; для відкритої proposed-зміни вони збігаються з чинними ID, revision, source_id та межами. Якщо після її створення чинна версія змінилася, пропозиція стає застарілою й не може застосовуватися без перегляду; це діагностика залишкової роботи, а не помилка історії. Для rejected та історичних applied перевіряють snapshots і граф, а не рівність старої версії поточній. Повторний опис тієї самої наявної версії у різних records має тотожні source_id/start/end. Незастосовані запропоновані After не є наявними версіями й не підтверджують Before іншої зміни. Нові ID резервує перший record split/merge; інший record не може заново оголосити їх новими.

Для boundary Before й After мають по одному рядку з однаковим scene_id та більшою revision в After. Для split — один Before та ≥2 After з новими scene_id й revision=1; для merge — ≥2 Before та один After з новим scene_id й revision=1. Applied After, якщо версія ще актуальна, збігається з scenes/index; якщо вже замінена — з Before наступної applied-зміни. Початковий Before може бути коренем історії; це не вимагає штучного запису створення сцени.

Для кожної пари scene_id/revision допускається щонайбільше один applied change_id, який її створює (After), і щонайбільше один applied change_id, який її замінює (Before). Рахуються різні change_id, а не ребра: кілька ребер одного split/merge не порушують правило. Коренева версія може не мати створювальної зміни, поточна — замінювальної. Pending/rejected у цей підрахунок не входять; при переході до applied перевіряється вся застосована історія. Ациклічності й однакових snapshots недостатньо: розгалуження S001/r1→r2 та r1→r3 різними applied-змінами й створення r4 із r2 та r3 різними applied-змінами відхиляються, навіть якщо подальші межі узгоджені.

Для одного scene ID допускається щонайбільше одна коренева версія без створювального applied change_id. Незв'язаний новий корінь не може відновити вже замінений ID: усі його наступні ревізії мають продовжувати ту саму історію. Основне непорожнє coverage використовує лише source_id=video; наявність суцільного audio-покриття не замінює обліку відео.

Приклад лише структурних блоків **умовної** proposed boundary; редакторські розділи й індекс у прикладі опущені:

## Change metadata

```csv
change_id,type,state,decision
CH001,boundary,proposed,pending
```

## Before

```csv
scene_id,revision,source_id,start,end
S001,1,video,00:00:20.000,00:01:00.000
```

## After

```csv
scene_id,revision,source_id,start,end
S001,2,video,00:00:20.000,00:01:05.000
```

Заголовки прикладу є ілюстрацією синтаксису всередині цього контракту; сам контракт не є change-record і не включається до індексу. Матеріали, причини, погодження й повнота їх перенесення залишаються предметом редакторського приймання; автоматичний парсер цих довільних таблиць не потрібний.

## Помилки та незавершені стани

Validator має відхиляти дублікати canonical ID, висячі source_id, невідомі scene/source ID, неприпустимі enum, некоректний час, цикл applied-змін, неправильні split/merge cardinality, суперечливі lifecycle/revision, розриви/перекриття непорожнього coverage, невідповідність scene-сегмента сцені, відсутній record/package-файл та unknown без note. Відсутність timing для використаної часової шкали — помилка.

Виняток до вимоги відомого scene ID: нові наступники proposed split/merge оголошуються в change-record і change-index, без запису в scenes/index або coverage. Перевіряються існування попередників, повнота й узгодженість оголошень, новизна ID, час і джерело. Наявність наступників у реєстрі вимагається при applied; це не дозволяє невідомі посилання в інших канонічних таблицях. Proposed boundary посилається на наявний ID із новою ревізією. Правила резервування та історії — у моделі.

Загальний рекурсивний обхід pipeline/validate.py виключає tests/fixtures/ з CSV та JSON-перевірок. Лише ізольовані тести передають кожну fixture як явний root scene_validation; інші канонічні каталоги залишаються під перевіркою.

Порожня карта та package без значення для ще не спланованої сцени дозволені з явним повідомленням «не побудовано/не сплановано». Неперевірена межа, unresolved і редакторське питання — видимий залишковий обсяг, а не автоматичний технічний збій; вони не означають завершеного аналізу.

Markdown-докази, повноту переліку матеріалів, обґрунтованість винятків часової належності, текст і драматичний поділ перевіряють за джерелом; validator не підміняє редакторське приймання. Історія змін не є дозволом на автоматичне застосування міграцій.
