# Implementation Plan: Обсяг роботи та змінюваний поділ фільму на сцени

**Branch**: `codex/004-scene-work-plan` | **Date**: 2026-11-08 | **Spec**: [spec.md](spec.md)

## Summary

Підготувати правила, формати, шаблон пакета сцени та перевірки, які дозволяють уточнювати карту фільму без втрати матеріалів. Повне транскрибування фільму виконується подальшими пакетами.

Сцена — робоча гіпотеза про відносно цілісну дію. Зміна місця, часу, складу учасників або цілі дії є підставою для перегляду, яку перевіряють за відео й звуком. Зміна плану сама по собі не доводить межу. Титри й переходи обліковуються у покритті без вигаданих драматичних сцен.

## Technical Context

**Language/Version**: Python 3.10+, стандартна бібліотека; українські Markdown-документи.
**Primary Dependencies**: чинний Spec Kit 1.3.2; без нових бібліотек, ASR/ML і медіазапусків у цьому пакеті.
**Storage**: CSV, Markdown; локальні медіа та звіти поза Git за docs/local-workspace.md.
**Testing**: pipeline/validate.py; майбутні ізольовані fixtures часу, історії та source_id.
**Target Platform**: Windows робоче середовище, Linux text CI.
**Project Type**: редакційний процес і перевірки репозиторію.
**Performance Goals**: перевірка текстових реєстрів без декодування фільму; штучного SLA немає.
**Constraints**: сталі ID, окремість P001, збереження погоджень; жодних машинних шляхів у Git.
**Scale/Scope**: один фільм, уточнювана кількість сцен; один актуальний пакет на сцену з історією попередніх.

## Phase 0 — Рішення та обґрунтування

[research.md](research.md): покриття та межі; сталі ID; історія split/merge; погодження; часові шкали; пакети сцен. Read-only дослідження агента виявило відсутність глобальної перевірки source_id та ризик відносних часових позначок. Його пропозицію центральної таблиці реплік розглянуто; обрано збереження чинної структури з глобальним пошуком ID, щоб не вводити новий спосіб зберігання.

## Phase 1 — Модель і процедура

[data-model.md](data-model.md), [контракт](contracts/scene-records.md), [перевірки](quickstart.md).

Майбутній порядок реалізації:

1. Узгодити формати й процедуру перенесення: ID походження не визначає поточного власника; часові шкали явні.
2. Підготувати порожні реєстри, шаблон результату та доменне доповнення до офіційного складеного spec-template.
3. Додати перевірки графа змін, покриття, source_id, статусів і часових шкал; порожня карта явно означає відсутність розмітки. Загальний рекурсивний обхід CSV/JSON у pipeline/validate.py має виключати саме tests/fixtures/, щоб навмисно некоректні дані перевірялися лише ізольованим тестовим runner. Перевірити, що така сама помилка в канонічних даних усе ще відхиляється.
4. Перевірити умовні boundary/split/merge, повторну зміну, перенесення репліки та відносного такту дії, складну сцену й пару сусідніх сцен.
5. Після tasks → analyze → implement → converge створити окремий пакет побудови реальної карти; за її результатом — пакети конкретних сцен.

Шаблон сцени визначає ID та ревізію меж, джерела, непевність, учасників, результати FR-009, особливості, залежності й приймання. Кожна сцена проходить повний цикл Spec Kit. Split/merge позначає старий обсяг заміненим, створює пакети наступників, переносить перевірені результати з походженням і явно перерозподіляє невиконану роботу.

## Спосіб виконання

Етап виконано за явно прочитаним speckit-plan; офіційний setup_plan.py створив складений шаблон. Поле BRANCH його JSON відображає обраний feature, фактична Git-гілка — codex/004-scene-work-plan. Before/after hooks відсутні: .specify/extensions.yml не існує. Phase 0 включає делеговане read-only дослідження за інструкцією skill; це не незалежне PR-рев'ю. GitHub review виконується окремо на опублікованому head.
