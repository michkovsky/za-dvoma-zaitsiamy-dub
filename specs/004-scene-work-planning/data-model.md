# Phase 1: модель даних

Проєкт майбутніх форматів; чинні таблиці в цьому PR не змінюються. Колонки — [контракт](contracts/scene-records.md).

## Сцена

Сталий id Snnn, назва, source_id=video, start/end, status, lifecycle, revision, package. status використовує чинні draft/verified/proposed/approved/rejected; lifecycle окремо active/superseded. revision — додатне ціле, зростає при зміні меж або складу. package — відносний шлях до актуальної spec.md або порожній для ще не спланованої сцени. Межі: 0 ≤ start < end ≤ duration. Історичні сцени залишаються в index, але не входять до актуального coverage.

## Сегмент покриття

id Cnnn, source_id, start/end, kind (scene/credits/transition/unresolved), scene_id, status, note. Для scene інтервал точно дорівнює поточним межам active-сцени; одна active-сцена має один сегмент. Інші види не мають scene_id. Впорядковані інтервали покривають [0,duration) без розривів/перекриття. Непевність позначається unresolved. Порожня карта допустима як початковий стан, але означає «покриття не побудовано».

## Джерело та тривалість

source/media.csv задає video/audio. Новий source/timing.csv: source_id,duration,reference_source_id,offset,note. duration — додатна тривалість; offset — секунди зі знаком, t_reference=t_source+offset. Video посилається на себе зі зсувом 0; audio — на video з перевіреним зсувом. Відсутність запису означає неперевірену часову основу. Якщо сталого зсуву недостатньо, перевірка відповідних стиків блокується до окремого рішення. Розмітка video не потребує готового audio-вирівнювання, доки не використовує audio-таймкоди.

## Зміна поділу

Markdown scenes/changes/CHnnn.md містить ID, тип boundary/split/merge, причину, докази, дату, таблиці до/після з ревізіями, попередників/наступників, рішення для всіх матеріалів, пакетів, посилань і погоджень, невирішене та стан proposed/applied.

Структурний індекс scenes/changes/index.csv: change_id,type,state,from_scene,from_revision,to_scene,to_revision,record. Один рядок на ребро; унікальний ключ change_id/from_scene/from_revision/to_scene/to_revision. Boundary має той самий ID і зростання revision; split — одного попередника й ≥2 нових наступників; merge — ≥2 попередників та одного нового наступника. Граф applied-версій ациклічний. Усі ребра одного change_id мають однакові type/state/record. Boundary двох сусідніх сцен — дві зміни, застосовані в одному коміті.

Applied-зміна й канонічні матеріали застосовуються атомарно в одному PR/коміті. Proposed не змінює чинне покриття. Для split/merge попередники стають superseded; для boundary актуальною лишається нова revision того самого ID. Подальша заміна наступника не стирає попередніх ребер.

У proposed split/merge попередники вже існують, а нові ID наступників оголошуються лише в таблиці після change-record та ребрах change-index. До applied їх не додають у scenes/index і coverage. Лише для нових наступників split/merge оголошення має містити ID, межі, джерело й початкову revision=1. Proposed boundary зберігає наявний ID та оголошує більшу revision й нові межі лише в change-record/index, не змінюючи поточні сцени й coverage. Обидва види оголошень перевіряються локально в пропозиції за точним форматом [контракту](contracts/scene-records.md#машинозчитувані-блоки-change-record).

Новий ID не може бути виданий іншій чинній, історичній чи зарезервованій proposed-сцені. При відхиленні пропозиції зарезервовані ID не перевидаються; state залишається proposed, decision у паспорті record стає rejected. Для applied decision=accepted, усі наступники повинні мати запис у реєстрі та перевірюваний зв'язок із відповідною історичною версією; актуальне coverage містить лише чинні active-версії. Історичні snapshots версій зберігаються в блоках before/after: автоматичній перевірці не потрібен доступ до попередніх Git-комітів.

## Репліка й належність

До чинних id,start,end,speaker,text,status,note додається source_id часової шкали video/audio. Це інше значення, ніж source_id перекладу, який лишається ID оригінальної репліки. Кожен canonical-рядок глобально унікальний і міститься лише в одному dialogue.uk.csv. Префікс ID — історичний; старі каталоги після перенесення не зберігають копію рядка. Належність часу перевіряється після приведення до video. Репліка, що перетинає межу, має одного основного власника та явні контекстні посилання у README сусідньої сцени; виняток належності документується в change-record або відкритих питаннях. Автоматичного розрізання репліки немає.

Speaker — відомий ID, навмисний хор відомих ID через + або unknown із note. Кандидати не видаються за хор. Непевні слова зберігають [?]. Для verified/approved із unknown потрібне явне прийняте обмеження: перевірка тексту не встановлює мовця автоматично.

## Пакет, матеріали та зв'язки

Пакет містить scene_id, source, revision, критерії, залежності, залишкову роботу й стан. Замінений пакет зберігає підсумок виконаного та посилання на наступників. Старі позначки виконання не стираються.

README сцени містить учасників (видимий/закадровий/непевний), диспозицію, докази, такти з джерельним часом, стан на вході/виході й питання. Таблиця зв'язків задає іншу сцену та її ревізію, часовий/змістовий зв'язок, докази, питання й рішення. Приймання розділяє межі, текст, пояснення, внутрішню й міжсценову перевірки; approved призначає лише власник.

## Інваріанти міграції

До зміни складається повний перелік матеріалів. Після неї кожен має одну долю: перенесений без змін, змінений із повторною перевіркою, контекстне посилання або явно невирішений. Невирішені пункти блокують завершення міграції. Старі відносні такти перераховуються через старий source-start; зміна контейнера не зсуває подію у фільмі. Погодження точного SHA лишається історичним фактом; нова збірка потребує нового приймання. P001 не стає сценою й не змінює ID чи performed-таймкоди.
