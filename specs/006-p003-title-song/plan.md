# Implementation Plan: P003 — заголовна пісня

**Branch**: `codex/p003-title-song` | **Date**: 2026-11-10 | **Spec**: [spec.md](spec.md)

## Summary

Окремий пілот: джерела й контекст → перший UK без підказки → локальний RU за доступності → попередня редакція → опис → другий UK → джерельне уточнення → англійський змістовий і співаний текст → коротка проба → повне відео. P001/P002 не змінюються.

## Technical Context

Markdown/CSV/JSON, Python 3.12, FFmpeg/FFprobe; повторне використання перевіреної Vulkan-збірки Whisper.cpp v1.7.6 і small q5_1 з P002. CPU без AVX2, FMA/F16C невідомі; GPU GTX 1650 4 GB. Перед ASR — короткий реальний probe й актуальний runtime. Синтезатор мовлення P002 не вважається синтезатором співу.

Початковий контекст UK: 00:00:50.000–00:02:30.000; це робочий вхід, не підтверджені межі пісні. Повноякісний PCM для музики, окремий mono 16 kHz для ASR. Два контрольні UK-проходи читають однакові байти й модель; змінюється лише описова підказка. Опис до другого проходу не містить готового тексту пісні.

## Implementation Sequence

US1 → US2 → US3. До кожного важкого нового інструмента — перевірка вимог офіційного джерела, ізольоване середовище й коротка реальна операція. Вокальне відокремлення та нотна розмітка — різні кроки. Англійська модель повинна підтримувати явні висоти/тривалості, або інший перевірений контроль вихідної мелодії. Голос нового виконавця не приписувати персонажу за відеокадром.

Перед остаточним T010 виконати T017: три окремі вокальні партії за уточненням користувача, зіставлення мотивів, метр/пульс та укладання складів. Спочатку коротко перевірити збережений Kim_Vocal_2.onnx із ORT 1.17.3/NumPy 1.26, потім відокремити лише контекст P003; усі виходи зовнішні. Висотні кандидати — librosa 0.11 pYIN на відокремленому вокалі після реальної короткої проби. Метр не визначається лише максимумом темпової автокореляції. Чернеткові MIDI й звуковий висотний орієнтир потрібні для перевірки, не видаються за підтверджені ноти. Це одноразовий аналіз; музичний pipeline загального призначення не додається.

## Заміна музичної основи за подальшим дорученням

Наданий користувачем нотний аркуш для баяна стає джерелом мелодії; верхня акордна схема — джерелом гармонії Am. Ручне прочитання восьми тактів куплета зберігається в pilots/P003/music/score.json у вихідній тональності C♯ minor. Пробний експорт транспонує на −4 півтони в Am; 110 BPM — редакторський параметр прослуховування, не перевірений темп фільму. Суми тривалостей дають чотири чверті на такт; 4/4 в експорті — явне редакторське групування, оскільки на зображенні числовий розмір не надрукований.

Один скрипт pipeline/render_p003_score.py на стандартній бібліотеці читає score.json, перевіряє тривалості, ліги й кількість складових атак, створює MIDI/MusicXML та синтетичні WAV мелодії, гітарного акомпанементу й міксу. Усі binary-виходи й manifest — у зовнішньому output-dir з перевіркою захисту оригіналів; існуючий каталог не перезаписується. Гітарний малюнок бас–акорд — редакторська демонстрація заданої гармонії, не розпізнана до ноти гітара фонограми. Шаблон повторюється для трьох куплетів без незалежного F0-переосмислення.

Перед реалізацією: FR-011 покритий T019–T021; суперечностей із збереженням джерел і статусів немає. Після реалізації перевірити числові тривалості, відсутність розривів ліг/зайвих атак, тотожність нот трьох повторень, структуру MIDI/XML, повне декодування WAV, clipping і SHA. Самої перевірки форматів недостатньо для приймання музики; відповідність фільму й точне розміщення складів залишаються предметом слухової звірки.

## Загальні перевірки

`pipeline/validate.py`, `git diff --check`, повне декодування створених уривків, фактичні довжини, SHA входів/виходів, порядок проходів. Прослуховування, правильність слів і співу перевіряються окремо. Немає обіцянки автоматичної якості ASR на музиці або чистого розділення монофонограми.
