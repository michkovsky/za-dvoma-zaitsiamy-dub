# Feature Specification: Керований процес змін проєкту

**Feature Branch**: `001-project-workflow`

**Created**: 2026-11-08

**Status**: Draft — на розгляд власника, без погодження злиття.

**Input**: User description: «Використовувати Spec Kit, готувати зміни через pull requests, передбачити участь інших моделей та документовані обмеження роботи Codex».

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Розглянути зміну перед прийняттям (Priority: P1)

Власник бачить цілісну пропозицію, причини, джерела та результати перевірки до включення її в прийнятий стан.

**Why this priority**: Прямі зміни в main приховували межу між пропозицією та погодженим рішенням.

**Independent Test**: Відкрити перший draft PR і перевірити, що його зміни відсутні в main, а мета, межі та перевірки доступні для оцінки.

**Acceptance Scenarios**:

1. **Given** доручена задача, **When** агент підготував зміну, **Then** вона перебуває в окремій гілці та draft PR, а не в main.
2. **Given** непогоджений PR, **When** перевірки пройшли, **Then** агент не зливає його автоматично.
3. **Given** погоджена версія, **When** додано змістовні зміни, **Then** власник має розглянути новий склад перед злиттям.

### User Story 2 - Продовжити роботу за відтворюваним процесом (Priority: P1)

Наступна сесія агента знаходить чинні правила й інструкції, відрізняє виконані етапи від планів і може продовжити без вигаданих можливостей інтеграції.

**Why this priority**: Назви каталогів і конституція самі по собі не означали фактичного застосування Spec Kit.

**Independent Test**: За інструкцією відкрити першу специфікацію, отримати її шаблон і перевірити наявність плану/завдань; звіт явно відрізняє перевірені можливості від неперевірених.

**Acceptance Scenarios**:

1. **Given** нова суттєва задача, **When** починається реалізація, **Then** їй передують визначені вимоги, план, завдання та аналіз узгодженості.
2. **Given** недоступний автоматичний виклик, **When** агент виконує етап, **Then** він читає відповідну встановлену інструкцію й чесно записує фактичний спосіб виконання.
3. **Given** звичайне уточнення репліки, **When** готується PR, **Then** можна послатися на чинну специфікацію без зайвого пакета документів.

### User Story 3 - Розглянути незалежні зауваження моделі (Priority: P2)

На доручення власника інша модель оцінює конкретне питання, а автор записує, які зауваження прийнято, відхилено або ще не вирішено.

**Why this priority**: Додаткове рецензування корисне, але не повинно створювати хибну впевненість чи обов'язкову залежність від іншої моделі.

**Independent Test**: За формою рецензії можна вказати модель, версію змін, предмет перевірки, докази та долю кожного зауваження; відсутність незалежної перевірки позначена явно.

**Acceptance Scenarios**:

1. **Given** доручена незалежна перевірка, **When** записано висновок, **Then** видно модель, коміт/контекст і обмеження, а не лише слово «погоджено».
2. **Given** моделі суперечать одна одній, **When** автор готує результат, **Then** розбіжність і її джерела залишаються видимими; злиття вирішує власник.

### Edge Cases

- Інша модель недоступна: позначити «не виконано», не імітувати незалежний висновок.
- Авторизація або push недоступні: зберегти локальну гілку, повідомити блокер; не обходити погодження.
- Нова сесія не виявляє skills автоматично: відкрити репозиторій як робочий каталог або прочитати встановлену інструкцію явно.
- Джерельні дані непевні: рецензія не знімає непевність без доказів.
- GitHub не блокує прямий push технічно: правила агента лишаються чинними; не заявляти ввімкнений захист гілки.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Усі подальші зміни MUST подаватися через окрему гілку та PR, без прямого запису агента в main.
- **FR-002**: PR MUST містити мету, межі, джерела, перевірки, відкриті питання та посилання на специфікацію або пояснення використання чинної.
- **FR-003**: Злиття MUST вимагати явного погодження власника на актуальні зміни; успішні перевірки не дають його автоматично.
- **FR-004**: Суттєві зміни MUST мати специфікацію, план, завдання й аналіз до реалізації та перевірку відповідності після неї.
- **FR-005**: Встановлення та робота процесу MUST мати зафіксовану версію, інструкцію відтворення й фактичну перевірку.
- **FR-006**: Обмеження Codex, доступність викликів і неперевірена автоматизація MUST бути описані явно. Уточнення наявної специфікації зберігає її вимоги/ID; read-only аналіз не змінює контекст наступних етапів; checklist вимог доступний до створення плану.
- **FR-007**: Установлення MUST зберегти чинні матеріали, ID, прийняті рішення й доменні skills; локальні середовища та секрети не публікуються.
- **FR-008**: Незалежна рецензія MUST позначати модель, перевірену версію, предмет, докази й обмеження; самоперевірка не є незалежною.
- **FR-009**: Кожне змістовне зауваження MUST мати явне рішення; відкриті блокувальні зауваження не можна приховувати.
- **FR-010**: Звичайні редакторські правки MUST проходити PR, але можуть використовувати чинну специфікацію замість нового пакета.
- **FR-011**: Перевірки текстових матеріалів MUST виконуватися без моделей, GPU та локального фільму; відсутні медіа не видаються за перевірені.
- **FR-012**: Поточне впровадження MUST бути надано як draft PR без злиття; стан процесу та залишкові обмеження видимі.

### Key Entities

- **Зміна**: задача, межі, гілка, версія, PR та стан погодження.
- **Специфікація**: вимоги, сценарії, критерії, план, завдання та результати перевірки.
- **Рецензія**: автор/модель, версія змін, предмет, докази, зауваження та рішення.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Для першої пропозиції власник може знайти всі шість частин: мету, межі, джерела, перевірки, відкриті питання та підставу процесу.
- **SC-002**: Усі 12 вимог мають визначений спосіб перевірки та відповідні завдання.
- **SC-003**: Перша зміна доступна для розгляду, а прийнята основна версія лишається незмінною до погодження.
- **SC-004**: Звіт не містить жодної заяви про виконане незалежне рецензування, автоматичний виклик чи перевірку медіа без відповідного фактичного результату.

## Assumptions

- Власник michkovsky приймає рішення про злиття; зовнішні моделі залучаються лише за дорученням.
- Наявна авторизація GitHub використовується без створення нових облікових даних.
- Ця задача не змінює переклад, склад персонажів, медіа або генератор дубляжу.
- Захист main і обов'язкові серверні approvals — окреме налаштування, тут не вмикаються.
- Повний пакет вимог потрібен суттєвим змінам; ретроспективно описувати ним весь фільм не потрібно.


## Review clarification — 2026-11-08

Copilot виявив три невраховані сценарії збереження контексту. FR-006 уточнено без зміни ID. Перед оновленням spec агент читає існуючі вимоги та зберігає їх. Read-only перевірка не створює/не переписує feature pointer. Checklist потребує наявного непорожнього spec, але не плану. Це уточнення тієї самої задачі; первинні сценарії й критерії лишаються чинними.
